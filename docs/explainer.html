Project walkthrough · Graph RAG

Yojana Mitra

యోజన మిత్ర · a scheme finder for Andhra Pradesh

A citizen describes themselves in English, Telugu or Hindi. The app turns that into a structured profile, uses a knowledge graph to decide exactly which government schemes they qualify for, and then explains each scheme from official text, with citations.

The one idea to remember: the LLM never decides eligibility. Eligibility is a strict rule question, so the graph answers it with exact rules. The LLM only does what it is good at: understanding messy language at the start and writing a friendly explanation at the end.

Step 1 · data/schemes.yaml

A knowledge base that code can read

One file lists 43 schemes (18 Andhra Pradesh, 25 central). Each scheme carries the text a person reads (amount, benefits, documents, steps, portal, sources) and its eligibility rules written as data. Here is the real rule list for Jagananna/AP Fee Reimbursement:

criteria:
  - use: ap_resident                       # a macro, reused by 18 schemes
  - {field: is_student,      op: is_true}
  - {field: education_level, op: in,  values: [intermediate, iti, polytechnic, degree, professional, pg]}
  - {field: social_category, op: in,  values: [SC, ST, BC, EWS, minority]}
  - {field: annual_income,   op: lte, value: 250000}
  - any_of:                                # OR: either one is enough
    - {field: studies_outside_ap,      op: is_false}
    - {field: outside_ap_admission_ok, op: is_true, assume: true}

Seven operators cover every rule: eq, in, gte, lte, is_true, is_false, any_in. assume: true means "if we don't know, assume yes but ask the person to confirm". Adding a scheme means editing this file only; the graph, search index and UI rebuild from it.

Loaded by yojana_mitra/schemes.py (expands macros, numbers the OR groups, gives each rule an id like annual_income|lte|250000 so identical rules become one shared node).

Step 2 · extract.py · extract_rules.py · profile.py

From a sentence to a profile

Input
"I'm 22 years old, family income below 1 lakh, studying BTech final year in Hyderabad, but I'm an AP citizen"
→
{ "age": 22,
  "is_student": true,
  "education_level": "professional",
  "annual_income": 100000,
  "state": "AP",
  "studies_outside_ap": true }

With a Groq key, extract.py sends the text plus a JSON schema to openai/gpt-oss-120b in JSON mode, then cleans the answer: any field that fails validation is dropped instead of crashing.

Without a key, extract_rules.py does the same with regular expressions in English, Telugu and Hindi: amounts in lakh, thousand or per month; acres, cents and hectares; AP district names; and it cuts out sentences about relatives so "my mother is 65" doesn't make you 65.

Derived facts (profile.py → derive()) are small calculations the rules can use directly: ap_resident from the state, income_within_ap_limit (₹1.2 lakh a year rural, ₹1.44 lakh urban), land_within_ap_limit, and so on.

Step 3 · graph.py · matcher.py

Graph matching with three answers, not two

The graph is (Scheme)-[:REQUIRES]->(Criterion): 43 scheme nodes, 71 criterion nodes, 195 edges. A rule like "Resident of Andhra Pradesh" is a single node shared by 18 schemes, which is why this is a graph and not a flat table.

Each rule is scored as one of three values:

+1 met 0 unknown: the person didn't say −1 not met

Inside an OR group, take the max (one yes is enough). Across all groups, take the min (every group must pass). The final value puts the scheme in a bucket: +1 eligible, 0 need more info, −1 not eligible.

Try it · Fee Reimbursement for the running example

Values start as the real profile above. Click to change any rule and watch the result.

Why three values matter: a yes/no filter would reject this student just because they never mentioned their community. Here the missing fact becomes a follow-up question. matcher.py ranks questions by how many schemes each answer could unlock (each scheme adds 1 ÷ number of facts it is missing, and three times that if the scheme is in the topic the person asked about), and shows the top five.

The same logic, twice

The Python function is the in-memory version (networkx, no database needed). The Cypher query does exactly the same in Neo4j. A test checks both give the same answer.

Python · graph.py
st, assumed = evaluate(rule, facts[field])
groups[g] = max(groups[g], st)   # OR
status = min(groups.values())    # AND
Cypher · MATCH_CYPHER
MATCH (s:Scheme)-[r:REQUIRES]->(c:Criterion)
... CASE ... END AS st
WITH s, r.group AS g, max(st) AS gst
WITH s, min(gst) AS status
Step 4 · intent.py

Show what was asked for first

This fixes the problem you found: asking about education and getting pension and gas schemes. detect_focus() looks for topic words in three languages (scholarship, fees, ఫీజు, छात्रवृत्ति, pension, hospital, house…). If none are present and the person is a student, it assumes education. Schemes in that topic go to the top, their questions are weighted three times higher, and everything else is folded under "You also qualify for".

The pension you saw was Atal Pension Yojana, a savings scheme you pay into. It is now labelled "retirement savings", not a welfare pension.

Step 5 · rag.py · explain.py

Retrieve the right passages, then explain only from them

Hybrid retrieval

Every scheme is split into small passages (eligibility, benefits, documents, how to apply…). Two searches run on each question:

  • Dense: multilingual-e5-small turns text into vectors, so it matches meaning and works for Telugu and Hindi questions.
  • Sparse: TF-IDF on words and character fragments, so exact names like "PM-KISAN" or "Aadhaar" always hit.

Reciprocal Rank Fusion merges the two lists. Each passage scores 1 ÷ (60 + position) in each list (position starts at 0), and the scores are added. A passage both methods like rises to the top. Illustration for "money for my college fees":

PassageDense positionTF-IDF positionRRF score
Fee Reimbursement · benefits011/60 + 1/61 = 0.03306
CSSS scholarship · benefits201/62 + 1/60 = 0.03280
PM Vidyalaxmi · benefits1–1/61 = 0.01639
Talliki Vandanam · benefits–21/62 = 0.01613

Positions are illustrative; the formula is the real one in rag.py → search(). The constant 60 stops a single first place from dominating.

Grounded explanation

The LLM receives three labelled blocks and is told to keep them apart:

A. CITIZEN FACTS   - Age: 22 · Student: yes · Income: ₹1,00,000 per year …
B. RULE CHECK      - met: Resident of AP, Currently a student, Income up to ₹2.5 lakh …
                     assumed: College outside AP admitted through the convener route
C. PASSAGES        - [1] Fee Reimbursement – eligibility: …  [2] … benefits: …

Rules, amounts, documents and steps may only come from C, each with its passage number like [2]. This split is the fix that raised faithfulness:

Before (one mixed prompt)
"You qualify because eligibility requires age 52." The person's age was copied in as if it were the rule.
After (A / B / C)
"Age 50 years or above – you told us: 52." The rule comes from the passage, the fact from the person.

Without a key, the same passages fill a fixed template, so the app still works offline.

The insight worth saying: precision stays near 0.99 everywhere, so the graph almost never recommends a wrong scheme. Every recall loss is an extraction miss (a fact the extractor didn't pick up), never a matching mistake. That is why the LLM extractor helps so much on the held-out set: recall goes from 0.726 with regex rules to 0.958 with Groq.

Faithfulness, in progress: after the A/B/C prompt fix, the first 7 re-scored answers went from 0.870 to 0.953. The full 40 finish once Groq's daily quota resets.

How to say it

Your pitch

30 seconds
"I built Yojana Mitra, a Graph RAG app that tells Andhra Pradesh citizens which government schemes they qualify for. You describe yourself in English, Telugu or Hindi; an LLM extracts a structured profile; a Neo4j-style knowledge graph checks the eligibility rules exactly; and RAG explains each scheme from official text with citations. On held-out profiles it reaches 0.98 precision and 0.96 recall, and I measured answer faithfulness with RAGAS."
2 minutes: add these three points
  1. Why the graph decides, not the LLM. Eligibility needs exact numeric rules and the same answer every time. LLMs can invent eligibility; rules can't.
  2. Three-valued logic. A missing fact means "unknown", not "no", so the app asks a follow-up question instead of wrongly rejecting someone, ranked by how many schemes the answer unlocks.
  3. What evaluation taught me. All recall loss came from extraction, so I switched to an LLM extractor. Most unsupported claims came from the model mixing up the person's facts with the scheme's rules, so I split the prompt into citizen facts, rule check and passages, and faithfulness went up.
Practice

Interview questions

Why use a graph instead of asking the LLM which schemes fit?

LLMs make mistakes with numeric limits (₹2.5 lakh, age 60+) and can invent eligibility. Graph rules are exact, the same input always gives the same answer, and every decision can be traced to a rule node. The LLM only parses language and explains the result.

Why is it a graph and not just a SQL table of rules?

Rules are shared: "Resident of AP" is one node linked to 18 schemes, and OR conditions are groups of edges. That makes questions like "which single fact unlocks the most schemes?" natural to answer, and it maps directly to one Cypher query. A table would work for matching, but the graph shows the structure and reuse.

What happens when the user leaves out information?

The rule scores 0 (unknown), so the scheme lands in "need more info" instead of "not eligible", and the app asks for the missing fact. Standard exclusions such as "no government employee in the family" are assumed and shown as "please confirm".

Why hybrid retrieval and why RRF?

Embeddings capture meaning and work across languages; TF-IDF catches exact names. RRF combines ranked lists using only positions, so there are no score scales to calibrate and no weights to tune.

What does faithfulness 0.91 mean, and how did you improve it?

91% of the small claims in the answers were supported by the retrieved passages, as checked by a judge LLM. Reading the 41 unsupported claims showed about half were the model writing the person's own value as the rule. Separating citizen facts, rule check and passages in the prompt took the re-scored samples from 0.870 to 0.953.

How did you avoid fooling yourself in evaluation?

I fixed extractor bugs using the 50-profile set, so its score is optimistic. I then wrote 15 new profiles and scored them once. The held-out number is the one I quote.

What are the limitations?

Scheme rules and amounts change, so the data needs updating. It is a pre-check, not an official sanction. Some rules can't be judged from a description (electricity use, property size). The Neo4j path has a parity test but hasn't been run against a live database in this environment.

Why Groq?

Free tier and fast inference on open models (gpt-oss) through an OpenAI-compatible API. The code also supports Claude, and runs fully offline with regex extraction and template answers when there is no key.

Learn the code in about an hour

Study plan

  1. Open data/schemes.yaml and read one AP scheme and one central scheme end to end.
  2. Read yojana_mitra/graph.py: evaluate() and MemoryGraph.match(), about 50 lines. This is the heart of the project.
  3. Read matcher.py → match_profile(): how statuses become buckets and how follow-up questions are ranked.
  4. Read the EXPLAIN_SYSTEM prompt in explain.py, then search() in rag.py.
  5. Run the app with python -m uvicorn yojana_mitra.api:app --port 8000, type your own profile, and watch /api/match in the browser's Network tab.
  6. Change one rule in the YAML (for example the income limit), restart, and see which schemes move.
